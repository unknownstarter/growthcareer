## 0. 노아 원문

> "템플릿 스타터는 결국 템플릿도 정리를 하지만, 이런 아이디어를 내가 내기만 하면 착착착 기획 → 디자인 → 개발 → QA → BM 리뷰 → 배포를 자동화해서 빠르게 프로덕트를 만들고 테스트 할 수 있게 하고 싶어. 지금 그로스커리어 프로젝트에서 계속 이런 얘기를 하는 이유는 웹 기반으로 프로덕트를 만들 예정이니까 여기에 있었던 디자인 시스템과 레슨런 들을 가지고 가고 싶어서 그런거야."

핵심은 **컴포넌트 모음이 아니라 파이프라인**이다. 그로스커리어는 인큐베이터 역할이고, 여기서 검증된 디자인 시스템과 운영 규율을 다음 프로덕트로 이전한다.

## 1. 스타터는 두 레이어다

혼동을 막기 위해 처음부터 분리한다.

### 레이어 A - 프로세스 팩 (진짜 차별점)

아이디어를 넣으면 배포까지 굴러가게 하는 규율과 에이전트 묶음. **이게 없으면 코드 템플릿은 그냥 보일러플레이트고, 리서치에서 본 ShipFast 처럼 금방 복제된다.**

이미 가진 것:
- 에이전트 9종 (`.claude/agents/`) - Aria, Echo, Sophia, Luna, Iris, Nova, Vera, Mira, Sage
- 운영 매뉴얼 (`CLAUDE.md`) - 12단계 워크플로우, Feature Intent Gating, 배포 전 5종 체크, 프로덕션 보호 룰
- 사고 레슨 인덱스 (`docs/lessons/`) - 9건, 전부 룰로 역반영됨
- 스킬 3종 (`.claude/skills/`) - grammar-checker, humanizer, style-guide
- 자동화 스크립트 83개 (`tools/`) - 캡처, PDF, E2E, 부호 검사

없는 것:
- **BM 리뷰 담당이 없다.** 로스터 9명 중 단가, 지불 의향, 유닛 이코노믹스를 따지는 역할이 비어 있다. Aria 는 프로덕트 가치, Sophia 는 기술 트레이드오프까지다
- 게이트 통과를 강제하는 훅이 없다. 지금은 규율이 문서로만 있고 사람이 지킨다
- 프로젝트 시작 시 이 팩을 새 레포에 심는 수단이 없다

## 2. 파이프라인 7단계와 게이트

| 단계 | 담당 | 산출물 | 통과 기준 (게이트) |
|---|---|---|---|
| 0. 리서치 | Echo | `docs/research/<date>-<slug>.md` | 파일로 저장됐는가. 출처 URL 있는가 |
| 1. 기획 | Aria | `docs/specs/B####-<slug>.md` | Feature Intent Gating 4문항 답변. 노아 승인 |
| 2. 디자인 | Luna | 토큰 시트 + 프리뷰 캡처 | 부호 검사 PASS. 캡처를 노아가 봤는가 |
| 3. 개발 | Luna / Iris / Nova | 코드 + 마이그레이션 | typecheck PASS. 기존 시그니처 미변경 |
| 4. QA | Mira | E2E 결과 | 시나리오 PASS. 재현 절차 기록 |
| 4.5 고객 검수 | **Cora** (신설) | 페르소나 통과 기록 | 첫 5초에 이해되는가. 이탈 지점이 어디인가 |
| 5. BM 리뷰 | **Juno** (신설) | 단가, 지불 의향, 유닛 이코노믹스 | 월 얼마를 누가 왜 내는지 답 가능한가 |
| 6. 배포 | Vera | 배포 로그 + 롤백 플랜 | 배포 전 5종 체크. 권한 변경이면 Sage 선행 |

**Cora 와 Juno 를 나눈 이유**: 돈이 되는가 (Juno) 와 처음 보는 사람이 이해하는가 (Cora) 는 다른 질문이다. 나머지 팀원은 전원 제품을 이미 아는 사람이라 처음 보는 사람의 막막함을 못 본다. Cora 는 제품 지식을 버리고 타겟 고객으로 빙의해 1인칭으로 보고한다. 단 **시뮬레이션은 실제 인터뷰의 대체재가 아니며**, Cora 의 보고서는 항상 인터뷰로 확인할 항목을 함께 남긴다.

지금 그로스커리어에서 돌고 있는 규율이 그대로 이전된다. 다른 점은 **5번 BM 리뷰가 새로 들어간다**는 것. 팬투프로는 이미 가격이 정해진 교육 사업이라 필요 없었지만, SaaS 는 유닛 이코노믹스가 틀리면 만들 이유가 없다.

## 3. 제일 중요한 원칙 - 첫 산출물은 SaaS 가 아니다

리서치 권고 2번이 "build first 가 아니라 distribution first" 였다. 이걸 파이프라인에 박는다.

**아이디어 1개당 첫 산출물 = 검증용 랜딩 한 장 + 대기자 폼.** 풀 제품이 아니다.

- 만드는 데 하루를 넘기지 않는다 (스타터가 있으니 가능)
- 유통 채널 한 곳에 뿌리고 2주 관찰
- 대기자 수와 전환율이 기준 미달이면 **버린다.** 개발 착수 안 함
- 통과하면 그때 3단계 개발로 내려간다

이 게이트가 없으면 마스터의 만드는 속도가 오히려 독이 된다. 빨리 만들 수 있으니 검증 없이 만들게 되고, ShipFast 사례처럼 유통 없는 제품이 쌓인다.

## 4. 레포 전략 (노아 결정 필요)

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. GitHub 템플릿 레포** | `product-starter` 레포를 만들고 Use this template 로 새 제품 시작 | 가장 단순. 제품별 완전 독립 | 스타터 개선이 기존 제품에 자동 반영 안 됨 |
| **B. 모노레포** | 하나의 레포에 `apps/*` 로 제품 추가, `packages/ui` 공유 | 디자인 시스템 개선이 전 제품에 즉시 반영 | 제품 하나 매각 시 분리가 번거로움. 배포 설정 복잡 |
| **C. CLI 스캐폴드** | `npx create-noah-app` 로 파일 생성 | 유연함. 나중에 공개하면 그 자체가 유통 자산 | 만드는 비용이 제일 큼 |

**추천: A 로 시작.** 리서치에서 exit 을 옵션으로 두라고 했는데, 매각 가능성을 생각하면 제품별 독립 레포가 유리하다. 스타터 개선분은 수동 체리픽으로 감당 가능한 규모다. 제품이 3개를 넘어가면 그때 B 를 검토한다.

## 5. 실행 계획 (3 phase)

**Phase 1 - 프로세스 팩 추출 (레이어 A)**
- `.claude/agents/` 9종을 제품 중립적으로 일반화 (팬투프로 고유 맥락 제거)
- `CLAUDE.md` 를 템플릿화. 프로젝트 고유 부분은 플레이스홀더로
- BM 리뷰 에이전트 신설
- 레슨 9건 중 도메인 무관한 것 (부호 검사, 프리뷰 wipe, SSG 캐시, Sage 선행, 리서치 파일 저장 등) 만 이식

**Phase 2 - 코드 스캐폴드 (레이어 B)**
- UI 7종 + 네비 8종을 브랜드 중립 토큰으로 분리
- Supabase + 인증 + RLS 기본 골격
- 없는 4개 중 **결제와 셀프 가입만** 추가. 멀티테넌시와 사용량 과금은 첫 제품에서 필요해지면 그때
- 검증용 랜딩 + 대기자 폼 템플릿 (3번 원칙의 도구)

**Phase 3 - 첫 제품으로 실전 검증**
- Echo 의 니치 리서치 결과에서 1개 선택
- 파이프라인 7단계를 실제로 한 바퀴 돌려본다
- 걸린 지점을 스타터에 역반영

## 6. 열린 질문

1. 레포 전략 A / B / C 중 무엇인가
2. BM 리뷰 에이전트를 신설할 것인가. 신설하면 이름과 성격은
3. Phase 1 과 2 중 무엇을 먼저 할 것인가. 프로세스 팩이 먼저면 첫 제품을 손으로 만들면서 규율을 검증할 수 있고, 코드 스캐폴드가 먼저면 만드는 속도가 즉시 빨라진다
4. 결제 수단은 무엇인가 (토스페이먼츠, 페이플, Stripe). 국내 개인사업자 대상이면 국내 PG 가 유리하다
