# 시각 효과 재현 - 레퍼런스 실제 구현부터 검사하라

날짜: 2026-09-21

## 무슨 일이 있었나

원티드 히어로의 "얼음 같은" 효과(글로시 오브젝트 + 텍스트 굴절/색분산)를 재현하려다 여러 번 헛발질했다:

1. 효과를 **오브젝트로 착각** → GPT 이미지로 "헤드폰" 여러 장 생성 (토큰·시간 낭비). 노아: "얼음 같은 효과를 물어본 건데 헤드폰 만드는 데 토큰 소비하냐."
2. 효과를 **라이브 2D 필터(SVG feDisplacementMap)** 로 흉내 → 원티드 대비 거칠고 퀄리티 안 나옴.
3. 뒤늦게 원티드 페이지를 실제로 검사 → **canvas/WebGL/three/spline 전부 없음, 정적 PNG 이미지**였음. 라이브 효과가 아니라 3D 툴에서 오프라인 렌더해 구운 이미지.

이 검사를 **처음에** 했다면 방향(정적 베이킹)을 바로 잡고 SVG/헤드폰 삽질을 안 했을 것.

## 왜 일어났나

- 레퍼런스의 "무엇처럼 보이는가"만 보고 **"실제로 어떻게 만들어졌나"를 검사하지 않음**.
- 사용자의 질문("얼음 같은 효과")을 내 가정(오브젝트 만들기)으로 치환.
- "AI는 이미지 생성"이라는 선입견으로 도구부터 잡음 (효과는 렌더링/셰이더지 생성 이미지가 아님).

## 어떻게 막을까

1. **시각 효과/디자인 재현 착수 전, 레퍼런스의 실제 구현을 먼저 검사한다.** Playwright로 DOM 검사: `<canvas>`+WebGL 컨텍스트 여부 / `<img>` 정적 에셋 / three·spline 스크립트 / `<video>`. "라이브 효과 vs 구운 이미지"부터 판정.
   → 역반영: CLAUDE.md §6 시각 검증 섹션에 룰 추가.
2. **사용자가 지목한 "효과"와 "오브젝트"를 분리 확인.** 무엇을 가리키는지 애매하면 레퍼런스를 다시 보고 되물은 뒤 착수.
3. **구현 know-how는 박제한다.** 재현에 성공한 기법은 `docs/design/webgl-glass-hero-technique.md` 처럼 how-to로 남겨 다음에 삽질 반복 방지.
